## Цель

Кастомная интеграция Home Assistant для контроллеров Larnitech через API2.
HA получает список устройств, их состояние (push + страховочный poll) и
управляет ими. Первая версия (v1) была read-only для двух типов виджетов
(`lamp`, `temperature-sensor`) — с тех пор покрыт практически весь каталог
типов Larnitech (актуторы, климат, шторы, сенсоры, входы/кнопки), включая
запись — см. "Карта маппинга типов" ниже для полного статуса по каждому типу.

## Подключение

Протокол, URL, авторизация, команды и протокольные нюансы (формат `status`,
ping, quirk `type:"json"`, таймауты) — в отдельном файле API:
`31_Larnitech/Knowledge/api2_connection_guide.md`. Здесь — только специфика
интеграции.

Режим (`local`/`cloud`) выбирается в config_flow.

**Мультисервер.** Один HA — несколько config entry, по одному на сервер
Larnitech. Каждый entry = отдельное WS-соединение, свой набор сущностей.

### Настройки и где они меняются

**Подключение** (`entry.data`) — меняется через **Reconfigure** (запись → ⋮ → Reconfigure):

| Поле | Режим |
|---|---|
| `connection_type` | оба (`local`/`cloud`) |
| `host` / `port` | local |
| `serial` | cloud |
| `key` | оба |

**Поведение** (`entry.options`) — меняется через **Options** (карточка
интеграции → Configure); при сохранении запись перезагружается. Все — **on**
по умолчанию, кроме `read_only` (**off**):

| Галочка | Что делает |
|---|---|
| `auto_remove` | удалять устройство, если пропало (отсутствует в **2 подряд непустых** снапшотах — не путать с полностью пустым снапшотом, см. ниже) **или сменило тип** (сразу) |
| `update_names` | подтягивать имена из Larnitech (ручные переименования не трогает) |
| `use_areas` | создавать комнаты как в Larnitech и раскладывать устройства |
| `update_areas` | переносить устройство при смене комнаты (требует `use_areas`; перезаписывает ручную привязку) |
| `read_only` | не отправлять `status-set` вообще — управление из HA (свет/switch/climate/...) откатывается: сущность сразу точечно перечитывается (`status-get`) и показывает реальный статус Larnitech. Единая точка гейта — `LarnitechEntity.async_write_status` |

Чтение: `toggle(entry, key)` = `options` → `data` → default `True`.

### Жизненный цикл (reconcile)

Только по **полному снапшоту** `get-devices` (не по событиям):
- **add** — платформы добавляют новые addr своего типа через `async_add_listener`;
- **remove** — координатор сносит device из registry (каскадом сущности), если
  конкретное устройство отсутствует в **2 подряд непустых** снапшотах, или
  сразу при смене типа (`device.model != new type`);
- **name/area sync** — обновляет имя/комнату в device registry по галочкам.

**Полностью пустой снапшот `get-devices` не доходит до reconcile вообще**
(баг найден и исправлен: раньше два пустых снапшота подряд удаляли **все**
устройства сразу, ложно принимая пустой/битый ответ за "у контроллера нет
устройств"). Теперь `_async_update_data` бросает `UpdateFailed`, если снапшот
пуст, а до этого данные были — сущности уходят в `unavailable` и
восстанавливаются на следующем нормальном опросе, ничего не удаляется.

Кнопка `button.<serial>_resync_names` (entity_category=config) — принудительно
сбрасывает все имена к Larnitech, **включая** ручные переименования.

## Поток данных (на уровне запросов)

Один `LarnitechClient` на config entry, одно постоянное WS-соединение.
Команды — в API-файле (`31_Larnitech/Knowledge/api2_connection_guide.md`).

### Инициализация
1. **Connect** — WS к `ws(s)://…/api`.
2. **Authorize** — `{"request":"authorize","key":"<key>"}` → ждём `result:success`.
3. **Полный снимок** — `{"request":"get-devices","status":"detailed"}` →
   наполняет `coordinator.data` (`{addr: device}`), создаёт сущности.
4. **Subscribe** — `{"request":"status-subscribe","status":"detailed"}` →
   сервер пушит изменения по этому же сокету.

### Рабочий цикл
1. **События.** `{"event":"statuses","devices":[…]}` применяются **напрямую**:
   merge изменившихся ключей статуса в нужный addr, без перечитывания всех
   устройств. Не-объект / неизвестный addr → фолбэк на полный `get-devices`
   (дебаунс 2 с).
2. **Страховочный poll.** Раз в N минут (сейчас **2**) —
   `{"request":"get-devices","status":"detailed"}`. Роль: восстановить
   пропущенные события, keepalive (сессия закрывается через ~5 мин простоя,
   2 мин < 5 мин), детект мёртвого соединения, reconcile (add/remove/rename).
3. **Запись из HA.** Изменение одной сущности → одна или несколько команд
   `status-set` на её `addr` (не весь список). Обычно одна; несколько
   **последовательных** (с паузой) — только там, где сам контроллер требует
   порядка между ключами и одновременная запись даёт неверный результат:
   `climate-control` `hvac_mode` off → `state:"off"` отдельно; `fancoil`
   heat/cool switch → сперва `mode`, пауза 1с, затем `state:"on"` отдельно;
   `valve-heating`/`fancoil`/`vent` turn-off с активным пресетом → сперва
   `automation:""`, пауза 1с, затем `state:"off"` отдельно (см. "Квирки и
   баги" — все три подтверждены живьём 2026-08-18). Формат значения —
   **object** (`{"request":"status-set","addr":"1:4","status":{"state":"on"}}`).
   Hex-форма (`"status":"0x01"`) тоже применяется, но ответ не содержит
   `success` (только `addr`) — поэтому используем object: он возвращает
   `{"addr":"1:4","success":true}`. По ответу / приходящему событию — обновляем
   состояние.

### Реконнект
Супервайзер переподключается с backoff; после реконнекта сразу повторяет
инициализацию (get-devices + subscribe).

### Обработка протокольных нюансов

Сам протокол — в API-файле (`31_Larnitech/Knowledge/api2_connection_guide.md`).
Здесь — как интеграция с этим работает.

- **Формат `status`.** Интеграция всегда запрашивает `status:"detailed"` (и в
  subscribe, и в poll) → статус приходит объектом. Событие несёт только
  изменившиеся ключи → **merge** в нужный addr, не replace. Не-объект / hex или
  неизвестный addr → фолбэк на полный `get-devices` (дебаунс 2 с).
- **Ping.** Облако не отвечает на WS-ping → `ping_interval=None`; keepalive и
  детект мёртвого соединения обеспечивает poll раз в 120 с.
- **Quirk `type:"json"`.** Клиент чинит `"status":{{` → `"status":{"_raw":{`
  перед `json.loads` (баланс скобок сохранён).

## Идентификация сущностей

- `unique_id` = `<serverSerial>_<ID>_<SUBID>` — `addr` формата `294:240`
  разбирается на ID и SUBID, префикс serial разводит одинаковые адреса на
  разных контроллерах. Пример: `411317ac_294_240`.
- `friendly_name` = `name` из get-devices как есть (язык клиента).
- Привязка к HA area — только если `create_areas = true`: area из Larnitech
  создаётся в HA и устройство привязывается к ней.

## Маппинг виджетов

### Версии 1–2 — чтение + запись

Поля подтверждены живым `get-devices`/`status-set` со стенда `411317ac`.

| Larnitech type | HA platform | Чтение | Запись |
|---|---|---|---|
| `temperature-sensor` | `sensor` | `status.state` (число); `device_class=temperature`, `°C` | — |
| `lamp` | `light` | `status.state` `"on"`/`"off"` → is_on (без яркости) | `status-set {"state":"on"/"off"}` |

Замечания по реальным данным:
- У `temperature-sensor` температура лежит в `status.state` (не отдельный
  ключ `temperature`). Значение — float, единица `°C`.
- У `lamp` помимо `state` есть `auto-state` (bool) — в v1 не используется.
- `addr` встречается с большими ID (`331:1`, `2048:247`) — разбор по `:`
  обязателен, не предполагать однозначные ID.

### Дальнейшие фазы

| Фаза | Содержание | Статус |
|---|---|---|
| 1 | Чтение lamp + temperature-sensor, polling | ✅ |
| 2 | Push (subscribe→refresh) + запись lamp (`status-set`) | ✅ |
| 3 | dimmer-lamp (brightness), AC (`climate`), cover, остальные виджеты | ✅ |

**Команда записи lamp (проверено):** `{"request":"status-set","addr":"1:4",
"status":{"state":"on"}}` → `{"response":"status-set","devices":[{"addr":
"1:4","success":true}]}`. Событие изменения: `{"event":"statuses","devices":
[{"addr":"1:4","status":"0x01"}]}` (on=`0x01`, off=`0x00`).

### Правило: один Larnitech `type` — один класс сущности

Каждому значению `type` (`AC`, `conditioner`, `fancoil`, `valve-heating`, ...)
соответствует свой класс, даже если протокол/поведение почти идентичны
соседнему типу (пример: `LarnitechAC` и `LarnitechConditioner` — общая логика
вынесена в `_LarnitechACBase`, но маски/бренч-специфичные баги живут каждый
в своём классе, не в `if is_ac` внутри одного). Поведение `sub-type` (когда
у типа есть подтипы, напр. `lamp`/`socket`, `lamp`/`pump`) реализуется
**внутри** класса своего `type`, не отдельным классом на sub-type.

## Квирки и баги Larnitech

Сводка всего, что найдено вживую и не является обычным протокольным поведением
— и странности дизайна, которые интеграция должна учитывать (квирки), и то,
что явно ведёт себя неправильно на стороне Larnitech (баги). Протокольные
низкоуровневые нюансы подключения (формат `status`, ping, `type:"json"`,
управляющие символы) — отдельно в API-файле
(`31_Larnitech/Knowledge/api2_connection_guide.md`), здесь — специфика
конкретных типов виджетов.

### Баги на стороне Larnitech

- **`fans`/`funs` (маска скоростей AC/conditioner) не приходит по API никогда.** (2026-08-14, повторно подтверждено 2026-08-17) Даже когда явно задана в XML (`fans="0x47"`, позже `fans="0x77"` — оба раза ключа нет в `get-devices`/`status-get`). Маска скоростей всегда берётся из дефолта (`0x1F` AC / `0x0F` conditioner) — реальную маску узнать через API нельзя.
- **`conditioner`: `modes` приходит, но со значением "как будто маски нет".** (2026-08-17) В XML стоял `modes="0x1A"`, `get-devices` вернул `"0x1F"` (все режимы) независимо от конфига. В отличие от `fans`/`funs` ключ **есть**, просто неверный. У `AC` тот же самый механизм отдаёт корректное значение (подтверждено на `1:101`: `modes="0x1A"` → HA показывает ровно off/cool/heat/auto). Пока не починят у вендора — `LarnitechConditioner` не читает `modes`/`funs` вообще, всегда полный дефолтный набор.
- **AC/conditioner: скорости 4/5/silent нечитаемы и незаписываемы.** (2026-08-14/17) Записать нечем: перебран весь словарь через `status-set` — число, `"5"`, `"speed5"`, `"silent"`, `"medium"` отвергаются с `code 9`. Прочитать тоже нельзя: `status.fan` приходит как raw `null`, когда физический блок фактически работает выше 3-й скорости, вместо какого-то нераспознанного сырого значения.
- **AC/conditioner: `target` сбрасывается в мусорное значение `-128`, если `status-set` при включении/смене режима не несёт `target` в том же вызове.** (2026-08-17, воспроизведено на `1:101`) Даже если до этого была валидная уставка (22°C, устройство выключено) — `{"state":"on","mode":"cool"}` без `target` в том же запросе даёт `status.target=-128.0` вместо сохранения прежнего значения. `{"state":"on","mode":"cool","target":21}` одним вызовом — работает корректно. Обход: `async_set_hvac_mode` теперь всегда включает `target` (текущий валидный или `min_temp`); `target_temperature` игнорирует значения вне `[min_temp, max_temp]` как sentinel.
- **`status-get` — "тонкий" ответ, только `addr`/`type`/`status`.** (2026-08-17) В отличие от `get-devices`, здесь нет `name`/`area`/`automations`/`modes`/`vane-hor`/`t-min`/... Не баг протокола как такового, но источник реальной порчи данных: наш `async_refresh_addr` (write-then-verify) сперва заменял им весь device dict целиком, стирая маски/имя/область при каждой записи — юзер заметил как пропажу `swing_horizontal_modes` у AC после любой записи. Исправлено — мержится только `status`.
- **`valve-heating`/`valve-cooling` (атрибуты на `fancoil`) не видны через API2 ни в одну сторону.** (2026-08-14, проверено напрямую запросом к API) Ни сами атрибуты на `fancoil`, ни обратная ссылка `fancoil=` на привязанных клапанах. Правило "нет клапана → фанкойл может только греть" нечем подтвердить в рантайме.
- **`light-scheme`: `ls-type` не приходит по API2 вообще**, только в XML-конфиге контроллера — узнать вживую, какой из 4 вариантов у виджета, нельзя. К счастью, форма статуса (`status.state` on/off) одинакова у всех вариантов, так что для маппинга это не мешает.

### Квирки дизайна (не баги — так задумано, но не то, что ожидаешь)

- **`lamp` sub-type `lock`: полярность инвертирована.** (2026-06/подтверждено 2026-08-14) `state=off` значит "заперто", `state=on` — "отперто".
- **`dimmer-lamp`/`rgb-lamp`: `level`/`saturation`/`hue` — целый процент 0-100, не дробь 0.0-1.0 и не градусы.** `hue` — позиция на цветовом круге **в процентах** (не 0-360°): выбор зелёного показывался оранжевым, синего — кислотно-жёлтым, пока не смасштабировали ×3.6.
- **`lamp` sub-type `closing-switch`** ("импульсный доводчик" по описанию) на практике — обычный persistent on/off switch, не импульсный/momentary выход.
- **`valve` (голый тип, не `lamp/valve-3`): словарь состояний `opened`/`closed`, не `on`/`off`.**
- **`status.fan` — разный тип значения по типам устройств, один и тот же ключ.** У `fancoil` — всегда float-процент 0-100, даже у явно ступенчатого устройства (`1:51` "Fancoil 3sp" отдаёт `66.4`, не индекс). У `AC`/`conditioner` — строка из фиксированного словаря `auto`/`low`/`middle`/`high` (средняя скорость на проводе — `middle`, не `medium`). У `vent` — число 0-100. У `virtual/ventilation` — строковый preset. Проверять по `type`, не полагаться на форму значения.
- **`valve-heating`/`fancoil`: всегда минимум 2 зарезервированных режима поверх именованных пресетов.** "Ручной" (`status.automation` отсутствует — синтетическая метка `"Manual"`, у Larnitech имени для этого состояния нет) и "always-off" (`status.automation="always-off"` на проводе, показывается как `"Always-off"`, не входит в XML-список `automations`).
- **Одно событие `statuses` может нести несколько устройств разом.** Частичный сбой декодирования одного устройства в пачке не должен ронять остальные.

| событие (decoded, прямое применение) | ~150 мс латентность | ~50 байт |

Раньше: каждое событие → полный `get-devices` (11 КБ). Теперь событие
применяется напрямую. Baseline-трафик при poll 120 с ≈ 8 МБ/сут (был 16 МБ
при 60 с), события почти бесплатны.

### Находка: websockets без `.open` (Python 3.14)

HA 2026.6 ставит новую реализацию `websockets` (`ClientConnection`) — у неё
**нет** атрибута `.open` (был в legacy). Проверка живости соединения через
`.open` падала с `AttributeError` на каждом poll после первого. Решение:
не проверять `.open`, а переподключаться при любом исключении send/recv.

### Находка: блокирующее создание SSL-контекста

`websockets.connect(wss://...)` строит SSL-контекст синхронно
(`set_default_verify_paths`) — HA ругается на blocking call в event loop.
Решение: контекст создаётся через `hass.async_add_executor_job(client_context)`
и передаётся в клиент параметром `ssl_context`.

**`fancoil`: переключение heat/cool требует раздельной записи `mode` и `state` (2026-08-18, по инструкции пользователя, проверено `watch_start`/`watch_read`).** Контроллер реагирует на смену `mode` тем, что сам на мгновение гасит канал (`state` → `off`), независимо от того, что пришло в том же вызове — подтверждено вживую дважды подряд (t=158.2→158.5→159.5 и t=175.2→175.5→176.5 в трассе события `statuses`: `mode` меняется, `state` тут же падает в `off` от самого контроллера, и только наша отдельная запись `state:"on"` секундой позже возвращает канал во включённое состояние). Одна комбинированная запись `{"mode":..., "state":"on"}` этот сбой не перекрывает — контроллер применяет свою реакцию на смену режима *после* неё. Рабочая схема: `{"mode": ...}`, пауза 1с (`_MODE_THEN_STATE_SETTLE`), затем отдельно `{"state": "on"}`.

Смена автоматизации (`automation` в событии) может изменить набор уставок целиком — по такому событию сразу дёргается точечное перечитывание, не дожидаясь страховочного 120-секундного опроса.

**Баг climate.py исправлен (найден и исправлен 2026-08-14, теперь общий только для AC/conditioner — `fancoil` выделен отдельно, см. строку 3):** `fan_mode` отдавал `status.get("fan")` без маппинга в `_attr_fan_modes` — `fancoil` вернул `0` (число) вместо строки из списка (это и навело на то, что фанкойл вообще устроен иначе, чем AC/conditioner). Для AC/conditioner осталось: строка — сверяется со списком режимов; число — используется как индекс в `_attr_fan_modes`; иначе `None` (не ломает фронтенд).

**Находка: `valve-heating`/`valve-cooling` у `fancoil` — конфиг-время атрибуты, через API2 не видны.** (2026-08-14, проверено напрямую запросом к API, в обе стороны — ни прямых ключей на фанкойле, ни обратной ссылки `fancoil=` на самих клапанах) Правило пользователя "нет клапана → фанкойл может только греть" нечем подтвердить в рантайме — `hvac_modes` поэтому статичный `[off, heat, cool]`, не зависит от факта привязки клапанов.

**Находка: словарь скоростей у `AC`/`conditioner` на проводе — только `auto`/`low`/`middle`/`high`.** (2026-08-14, перебран весь словарь через `status-set` на обоих живых устройствах) Нумерованная схема из документации (1st..5th speed, silent mode) — это UI-названия и позиции битов в маске, **не значения API**. Число (`{"fan": 2}`) и любое другое слово (`"silent"`, `"medium"`, `"1"`) отвергаются с `code 9: set-status has invalid parameter`. В HA показываются как `Auto`/`1st Speed`/`2nd Speed`/`3rd Speed`, на провод уходит соответствующее имя. Биты 4-6 маски (4-я/5-я скорость, silent) адресовать нечем — ждут появления устройства, которое их отдаст.

**Находка: маски приходят по API, кроме `fans`/`funs`.** (2026-08-14) `modes` и `vane-hor` появляются device-level ключами, как только заданы в XML (проверено: у `1:101` после добавления `vane-hor="0x7F"` он тут же появился в `get-devices`). А вот `fans` не приходит **никогда**, даже когда явно задан (`fans="0x47"` у того же `1:101`) — поэтому маска скоростей всегда берётся из дефолта.
